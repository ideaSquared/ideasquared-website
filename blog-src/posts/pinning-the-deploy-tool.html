One dependency with the keys

Each product repo calls shipper’s reusable workflows. Those workflows check out shipper’s own scripts and run them with the Cloudflare token. That makes shipper a dependency with more reach than any library in a product. A change to it runs in every product’s next deploy.

This post is about how a change gets there. It is not about an incident. Nothing in the history says anything went wrong. We wanted the answer to be a decision, not a side effect.

14 November: v1 follows main

Products used the v1 tag. On 14 November, commit 6308da4 made the tag move by itself. A release-v1 job in shipper’s CI ran on every push to main, after the tests passed, and moved v1 to that commit. A commit marked breaking (feat!: or a BREAKING CHANGE footer) left the tag where it was.

It was simple. The effect was that a green merge into shipper reached every product’s next deploy with no further step.

21 November: v1 moves only by approval

Ticket ENG-1511 changed that. Commit 5ced319 removed the push-triggered job. Now v1 moves only through a manual run of release.yml. Its comment says why: callers on @v1 pick up whatever v1 points at, with the Cloudflare token in reach.

The workflow has two jobs. verify runs first, and refuses a commit that:

  • is not on main;
  • has not passed the test check;
  • is marked breaking since v1, so it needs a new major tag by hand.

Only then does release run, and it runs in a protected GitHub environment called release, which needs a reviewer to approve. Verification comes first so that the reviewer is only ever asked about a commit that is on main with green tests.

Pin to a commit, not a tag

The same commit changed what we tell products to do. The README now says to pin shipper to an exact commit SHA, never to a tag or branch, because a moving ref would let any change to shipper reach production unreviewed. A product pins two things to the same SHA: the uses: line, and the shipper-ref input, which says which version of the scripts the workflow checks out. The input’s default stays v1 for callers still on @v1.

Two pins can drift. Dependabot updates a uses: SHA but does not know about shipper-ref. So products carry a CI step that fails unless every shipper pin is a full 40-character SHA and all of them match. ideasquared-website added it on 22 November, then tightened it to fail on a tag or a missing shipper-ref. agent-idea had moved to a pinned SHA the day before, and its check was fixed to read quoted values and skip commented lines.

22 November: the rest of the chain

If shipper is pinned, shipper’s own supply chain matters too. That day:

  • shipper pinned its own GitHub Actions to full commit SHAs, with a version comment on each (85f0bdb), and added Dependabot for npm and GitHub Actions;
  • the release workflow began creating a vX.Y.Z tag and a GitHub Release, with package.json at 1.0.0, and checks before the approval that the version is a new 1.x.y;
  • a release runbook went into the README (9606287).

Then products moved to the SHA commented v1.0.0. agent-idea moved from its earlier SHA pin, and ideasquared-website from @v1. Each commit is titled “pin shipper workflows to v1.0.0”.

The runbook

Five steps: merge with the version bumped and a changelog entry; run the release workflow and approve; merge the product repos’ bump pull requests; let developer machines pick it up through eng; and, if a release is bad, revert the change in shipper and release a new patch. The last step carries the point of the whole design. Product repos keep their old SHA until they merge the bump, so nothing moves without a pull request.

What we learned

  • Decide how a change reaches production, then build the path. Moving a tag after green CI is a path too, but one nobody chose. Now each step has a person or a pull request in it.
  • Put the checks before the approval. A reviewer should be asked only about a commit that already passed the mechanical rules.
  • Two pins need a check. A tool that updates one of them will not always update the other. Make CI say so.
