Why one afternoon

The new engineering standards landed in eng on 22 November. Several of their rules are about what we let into a build: other people’s actions, other people’s packages, other people’s tags. The commit times that day, in UTC, run from 12:33 (eng) to 13:35 (agent-idea). One afternoon, four repos: agent-idea, shipper, eng and this website.

These controls do not make us safe. Each one closes a specific door. Here is each door.

Actions pinned to commit SHAs

A tag like actions/checkout@v5 can be moved by whoever controls that repo. A full 40-character commit SHA cannot. As of 28 November, the four repos have 54 uses: lines in their workflows, and all 54 are pinned to a SHA with a version comment: 12 in agent-idea, 20 in shipper, 4 in eng and 18 in this site. That counts lines, not different actions, and it includes shipper’s own reusable workflows, which agent-idea and this site pin too.

Pinning stops a moved tag changing what runs in our CI. It also stops updates arriving on their own, which is why the next control exists.

Dependabot with a cooldown

All four repos have Dependabot for npm and for GitHub Actions, weekly, with minor and patch updates grouped into one PR. Each sets a three-day cooldown, so Dependabot skips versions published in the last three days. That stops us taking a bad release in the hours before anyone notices it. (agent-idea’s GitHub Actions entry came a day earlier, on 21 November.) Dependabot also bumps the pinned SHAs, so pinning does not mean going stale.

One small inconsistency: a comment at the top of this site’s dependabot.yml still says shipper is referenced by its moving @v1 tag. The workflows now pin a SHA. The comment is wrong, not the pin.

pnpm supply-chain settings

shipper, eng and this site have a pnpm-workspace.yaml with minimumReleaseAge: 1440 and trustPolicy: no-downgrade.

  • minimumReleaseAge makes pnpm refuse any version published less than 1,440 minutes (24 hours) ago, so a freshly published bad version is not installed.
  • trustPolicy: no-downgrade fails an install when a version has weaker publishing evidence than earlier ones, so a package that quietly lost its trusted publisher is not accepted.
  • allowBuilds lists the only packages allowed to run install scripts. eng and this site also set strictDepBuilds and blockExoticSubdeps, which fail on unreviewed build scripts and on transitive dependencies fetched from odd places.

The honest part: agent-idea does not have these two settings. Its file lists the workspace packages and an allowBuilds for esbuild and workerd, and nothing else. In the standards this is COMMON-06, a SHOULD, so it is not in the MUST gap tables. It is still a gap.

This site shows what the settings cost. Its file has a trustPolicyExclude entry for one exact version of chromium-bidi, which comes in through the Lighthouse CI tool. That version was published without the trusted-publisher evidence earlier versions had, and no-downgrade refused it. The comment says the tool is dev only, never deployed, and to revisit when Lighthouse moves on. We made an exception, wrote down why, and named the exact version.

SECURITY.md

All four repos have a SECURITY.md saying how to report a vulnerability privately and what to expect. shipper’s promises an acknowledgement within three working days. A policy with no way to follow it is worse than none. The website’s commit says GitHub’s private reporting must be switched on in repo settings by the owner, and we cannot check that setting from the files.

dist/ checks and release tarballs

agent-idea, shipper and eng commit their dist/ folders, because the CLIs install straight from GitHub with pnpm add -g github:ideaSquared/<repo>. CI rebuilds and fails if git status shows any difference, new files included. That stops a committed build that does not match its source. This site has no dist/, so has no such check.

For @ideasquared/log we went a step further, but earlier: on 14 November, not 22. Products install it from a tarball on a GitHub Release, and their lockfile pins it with an integrity hash. The README says not to use a git URL or a github: spec. A tarball with a hash cannot change under you. A branch can.

What we learned

  • Controls come in pairs. Pinning needs Dependabot, and Dependabot needs a cooldown. Any one alone either goes stale or moves too fast.
  • Write the exception next to the setting. The chromium-bidi comment says why, how narrow it is, and when to look again.
  • Audit your own list. Writing this post found a missing setting in agent-idea and a stale comment on this site.
