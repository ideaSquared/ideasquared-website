Every leak becomes a test: a field guide to our sanitiser.

Our log sanitiser is never finished. It is a list of everything that got through once. Here are the leaks, and the test line each one left behind.

  • By Alex Jenkinson, with support from Claude
  • 28 Nov 2026
  • 4 min read
  • Covers 14 to 21 Nov 2026
  • ideaSquared/agent-idea

The rule

The sanitiser in Agent Idea has one rule that matters more than the rest: if it does not recognise something, it does not let it through. Fields are on an allowlist. Anything else is dropped or replaced. Our CLAUDE.md adds a second rule for people working on it: add a line to the PII test lines for every new kind of leak.

The result is that test/sanitise.test.ts reads like a field guide. Each line is a log message that once got through, or could have. Each is checked the same way: scrub the line, then assert that none of the listed values survive.

it.each(PII_CORPUS)('removes personal data and secrets: $line', async ({ line, leaks }) => {
  const scrubbed = await scrubText(line, KEY, RULES);
  leaks.forEach((leak) => expect(scrubbed).not.toContain(leak));
});

All the values below are made up. We have left out anything shaped like a real key.

Keys that were not on the list

On 14 November, review found that the secret rule matched names such as token= but not refresh_token=, csrfToken: or "refreshToken":"...". It also missed credentials inside URLs when there was no username, like a Redis password or the key in an error-tracker address (fdc5675). The fix matched any key whose name contains a word like token, secret or password. The tests:

{ line: 'refresh_token=abc.def.ghi rejected', leaks: ['abc.def.ghi'] },
{ line: 'redis://:s3cretpw@redis:6379 AUTH failed', leaks: ['s3cretpw'] },

A week later, the 21 November review (ticket ENG-1504) found the same weakness from the other side. Names that end in _KEY were not caught, and neither were Stripe-style keys, which start with sk_live_ or sk_test_ (d97d6ce). The rule now looks for the word anywhere in the name:

{ line: 'env STRIPE_SECRET_KEY=dummyvalue123 loaded', leaks: ['dummyvalue123'] },
{ line: 'config secret_key: s3kr1tvalue set', leaks: ['s3kr1tvalue'] },

The same commit made a Cookie header redact to the end of the line, and any Authorization value redact whatever its scheme. A follow-up (38fa06c) closed two gaps in that: a Digest header with several parts, and a quoted password with an escaped quote inside it, where the text after the quote used to survive.

Emails that were not ASCII

The first email pattern only knew plain letters. A name with an accent walked straight past it. The 21 November fix switched to Unicode letters, and allowed the @ to arrive URL-encoded as %40:

{ line: 'send to zoë@example.com failed', leaks: ['zoë', 'example.com'] },
{ line: 'send to jo%40example.org failed', leaks: ['jo%40', 'example.org'] },

That left one more shape: an accent written as a separate combining mark, not as one character. The second commit added combining marks to the pattern and a test written with an explicit ́. It looks the same on screen and is different text.

Things that only looked like routes

Not every leak is a secret. On 14 November, review found three gaps in a single commit (d837dd8). One was about routes. A path such as /api/v1/creators/some-handle carries a person’s handle in plain sight. So each project now has a list of known route words, and every other segment becomes :param. A word that takes an id, like creators, hides the next segment even if it is a known word. And parameter syntax in a raw path is not trusted, because a caller can write :something too:

expect(event.route).toBe('/api/v1/creators/:param');
// a raw path claiming to be a template is not believed
{ route: '/api/:name/images/{name}' }  // becomes /api/:param/images/:param

The same commit made search run over sanitised events instead of Cloudflare’s own search. Otherwise a search for a name could reveal, by returning a result or not, whether it was in the raw logs.

Free text we stopped trusting at all

The best fix on 15 November (78d091d) was to delete something. Error titles from GlitchTip are free text, and a free-text message can name a person. We could have scrubbed harder. Instead the API now returns only the exception type:

// 'TypeError: cannot read owner of <a name>'
expect(title).toBe('TypeError');
// a title with no recognisable type at all
expect(title).toBe('Error');

The same commit templated the routes in culprits, dropped any culprit it could not read, scrubbed stack frame paths, and moved the length limit to after scrubbing. Clipping first can cut a secret in half and leave the part the pattern no longer recognises.

What we learned

  • Fail closed beats a better pattern. Allowlisting a field, or returning only an error’s type, removes a whole class of leak. A smarter regex only narrows it.
  • Write the test line first. A leak found in review becomes one line in the list. The list is how we know the next change did not bring it back.
  • Order matters. Scrub before you clip, and match secrets before anything else, so a token is never half-matched as something harmless.
  • Leaks come in families. A suffix one week was a prefix the next. We now look for the family when we add the line.
