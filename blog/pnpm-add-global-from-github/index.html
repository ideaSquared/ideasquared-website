Shipping a CLI with pnpm add -g github:.

Our CLIs install straight from GitHub, with no npm publish. It works, but pnpm has rules about it. Here are the errors we hit, with their exact codes.

  • By Alex Jenkinson, with support from Claude
  • 28 Nov 2026
  • 3 min read
  • Covers 15 to 22 Nov 2026
  • ideaSquared/eng

Why install from GitHub

eng, ship and idea are not on the npm registry. Each is installed from its GitHub repo:

pnpm add -g github:ideaSquared/eng

That keeps releases simple: the repo is the package. The cost is that pnpm treats a package installed this way with suspicion. We hit three separate problems in eight days. This post is about those, in the order they happened. For the wider story of the tool, see building eng.

ERR_PNPM_EXOTIC_SUBDEP

On 15 November eng update started failing with ERR_PNPM_EXOTIC_SUBDEP. pnpm refuses URL and git dependencies of a package that is installed globally from GitHub. eng depended on @ideasquared/ops by release URL, so pnpm refused it.

It hurt more than one tool. ship, idea and eng are installed in one command, so when eng failed, none of them updated.

The fix, in commit 12546fe, was to vendor the client. eng now carries the three files it uses (contract, args and client, from ops-v0.1.1) under src/vendor/ops, and takes zod from the registry. Then we added a test so the problem cannot come back quietly. It reads package.json and fails if any runtime dependency looks like a URL or path:

const exotic = Object.entries(dependencies).filter(([, spec]) => /[:/]/.test(spec));
expect(exotic).toEqual([]);

The test comment says why: every runtime dependency of a globally installed package must come from the npm registry.

ERR_PNPM_GIT_DEP_PREPARE_NOT_ALLOWED

On 22 November, a standards sweep added commit linting with husky. The husky hook was installed by a prepare script in package.json. The script was written to do nothing where husky is absent, as in global installs.

That was not enough. A non-empty prepare script makes pnpm add -g github:ideaSquared/eng fail with ERR_PNPM_GIT_DEP_PREPARE_NOT_ALLOWED. Commit 26262be dropped it. Contributors now run pnpm hooks:install once instead, and the README says so.

shipper had the same problem, and the same fix the same day: commit 43d3f20, “drop the prepare script”, with hooks:install as an explicit script.

Committing dist/

Both errors point at one design choice. Nothing builds on the user’s machine, so the built dist/ folder is committed. Both CLAUDE.md files say so: it is what the install command fetches.

CI enforces it. After pnpm build, it fails if git status --porcelain -- dist prints anything. We use git status and not git diff because git diff misses a file that the build creates but nobody committed. shipper’s commit e0621cc made that change, and eng took the same check.

CI also packs the repo, installs the tarball globally and checks that --version matches package.json. That tests the packed CLI. It does not run the GitHub install itself, which is why the two errors above reached us in use.

pnpm 11 and stale shims

The third problem was quieter. pnpm 11 moved global bins to PNPM_HOME/bin. Shims for ship, idea and eng left by pnpm 10 could sit earlier on the PATH and win. An update then looked as if it had failed, because the old copy kept running.

On 22 November we made four changes:

  • eng doctor finds every PATH folder holding each tool, fails when there is more than one or the first is not pnpm’s global bin, and shows each tool’s --version (7d2b509);
  • after pnpm add -g, eng update runs the same check and records the install only when it passes (7d2b509);
  • the installers put pnpm bin -g first on the PATH and remove stale shims, touching only those three names and only files that look like pnpm shims, so they stay safe to re-run (2ad5dff);
  • the PATH scan follows the shell: an empty entry is the current folder on Linux and macOS, and a directory or a file without an execute bit is not a match (c6f89ba).

shipper’s README now says the same for pnpm 11: run pnpm setup (11.15.1 or newer) and use which -a ship or Get-Command ship -All to find a stale copy.

What we learned

  • Test the install, not only the code. Both pnpm errors came from package metadata, which unit tests do not cover. A test over package.json caught the first class of error for good.
  • A harmless hook is not harmless everywhere. A prepare script that does nothing still counts as a script to pnpm.
  • Check which copy runs. After a tool manager changes where it puts binaries, “installed” and “running” can be different files.
