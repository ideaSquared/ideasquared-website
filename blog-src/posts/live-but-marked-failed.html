A deploy that is both done and failed

On 20 November we added smoke checks to shipper. A health check proves one component answers. A smoke check requests real pages after every component has deployed and passed its health check. The commit gives the reason: one health URL per component stayed green while real pages were broken. Its examples are a CSP blocking the API and a Worker answering on the wrong hostnames.

A failed smoke check fails the deploy job. It does not roll back. The commit explains why: a smoke failure can come from a dependency, so rolling back might fix nothing. The message suggests ship rollback and leaves the decision to a person.

That choice has a consequence. The new release is already serving traffic, and the job is red. Those two facts did not fit the two states we had.

The states we had

shipper records each deploy as a GitHub Deployment, with a status. Until that day it wrote success or failure. Everything that came later read those two words:

  • the gate for the next environment asks whether a commit has a success in each environment it requires;
  • the stale check asks what is live and compares the new commit against it;
  • ship rollback asks what is live and picks the newest earlier release that was live.

A smoke-failed release was written as failure. So the record said it was not live. It was.

First fix: 20 November

Commit 86d24c3 says it plainly: a smoke-failed release is live but was recorded as failure, so ship rollback skipped the last healthy release. The fix added a third state. A smoke failure is now written as error, and the type says what each word means:

// `error`: deployed and live, but its smoke checks failed.
// `failure`: not live.
state: 'in_progress' | 'success' | 'failure' | 'error'

error still keeps the release out of requires, because it is not success. And rollback now treats a newest deployment in the error state as the one running. The test builds exactly that case: a newer release went live, failed smoke, and rollback goes to the last healthy commit instead of saying that commit is already live.

The same commit tightened smoke output. A missing expect text is reported without echoing the text, and smoke URLs must parse as https URLs.

Second fix: 23 November

The first fix was narrow. It looked at the newest deployment only. If a newer deploy then failed, the smoke-failed release was hidden behind it, and rollback could pick the wrong release again.

Commit 83b8b47 gave the idea a name and one place to live. lastLiveDeployment returns the newest deployment that either reached success or whose latest status is error. A newer failure, or a deploy still running, no longer hides it. Statuses come newest first, so the code reads the first one.

Then every place that used “last successful” to mean “what is running” was switched over:

  • the stale check, so an older commit is refused over a smoke-failed release too;
  • the previous commit shown in the deploy preview and the Discord commit list;
  • ship diff, the CLI deploy gate and ship rollback.

Two things stayed on success only: requires and deployedTo. That is deliberate. An environment that requires staging will not take a commit that failed smoke there, even though staging is serving it.

What we do not know

We found this by reading the code against the states. Nothing in the commits says a rollback went wrong in a real incident, and we do not claim one did.

What we learned

  • Define the states before you automate on them. We built the gate, the stale check and rollback on success and failure before we had decided what to call a release that is live and failing a check.
  • “Live” and “healthy” are different questions. Each caller should ask the one it means. After the second fix, one function answers “what is running” and the rest ask it.
  • Fix the concept, not the caller. The first fix patched rollback. The second named the idea, and the other callers followed.
