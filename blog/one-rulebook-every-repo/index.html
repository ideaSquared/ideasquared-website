One rulebook for every repo.

Eight repos, one person, evenings only. We wrote the rules down once, made each one checkable, and let a weekly sweep find where a repo has drifted.

  • By Alex Jenkinson, with support from Claude
  • 28 Nov 2026
  • 4 min read
  • Covers 22 to 24 Nov 2026
  • ideaSquared/eng

One folder, six files

On 22 November we added standards/ to eng. It holds the engineering rules for every ideaSquared repo. One file, common.md, applies to all of them. Five more apply by repo type: cloudflare-app.md, vps-app.md, cli-tool.md, static-site.md and frontend.md.

A table in the README says which repo is which type. A repo can have more than one. The marker for each type is a file you can look for: a wrangler.jsonc with a Worker script, a docker-compose*.yml plus a Dockerfile, a bin entry pointing at a committed dist/. If the table and a repo disagree, the markers win and the fix is a PR to the table.

What a rule looks like

Every rule has an ID, a level, one sentence and a Check: line. Counting the files on 28 November, there are 151 IDs: 41 in common, 25 for Cloudflare apps, 31 for VPS apps, 15 for CLIs, 18 for static sites and 21 for frontends. 115 are MUST, 32 are SHOULD and 4 are retired.

Here is one in full:

COMMON-03 · MUST · Every actions/setup-node step reads the
version from the repo (node-version-file: .nvmrc),
never a hard-coded node-version.
Check: grep -rn 'node-version:' .github/workflows
is empty, and every setup-node step has node-version-file.

The Check: line is the point. A rule that says “keep dependencies tidy” cannot be checked. A rule that names a file, a key and a value can be, by a script or by an agent.

MUST and SHOULD mean different things. A repo that breaks a MUST has a gap, and the sweep opens a PR. A SHOULD is the default, and a repo can depart from it by writing the rule ID and one line of why in its CLAUDE.md under ## Standards exceptions. A MUST cannot be excepted. You change it in eng, by PR. IDs are never reused: the four retired ones are the Netlify rules, kept with the reason, after we decided to move static sites to Workers static assets.

Decisions that are not up for debate

The top of common.md lists decisions the owner has made: Node.js 24 LTS, Dependabot not Renovate, pnpm workspaces, deploys through shipper, logging through @ideasquared/log, Conventional Commits, strict TypeScript. We recorded the later ones on 22 November, including that code-owner review is recommended, not required, while the org has one maintainer. Reopening one needs the owner’s approval on the PR. The sweep never changes a rule.

The sweep

The README describes the Consistency sweep as a weekly scheduled task. For each repo it reads the rules that apply, runs each Check: against the default branch, and skips excepted SHOULD rules. It opens at most one PR per repo, titled chore(standards): close <n> gaps, with one commit per rule ID. Gaps that need a person, such as repo settings and secrets, go in the PR body. Then it updates the “Current gaps” tables.

What we can show is narrower than the design. In the four repos we hold, only agent-idea has “close N gaps” commits. #22 closed 19 gaps on 22 November, about an hour and twenty minutes after the standards first landed. #32 closed 2 on 24 November. shipper and this website each have a single chore(standards) commit from 24 November, and the tables cite open PRs in creatrgrid, pairflix and adopt-dont-shop that we have not looked at here. The tables carry one sweep date, 24 November.

What the gap tables said

On 24 November the common table listed 13 MUST gaps, the CLI table 1, and the frontend table 24 (accessibility, design-system and UX rules). The Cloudflare, static-site and VPS tables listed none. Of the 13 common gaps, five had a PR open against them. Eight needed a person: no branch ruleset, no required status checks, or secret-scanning push protection off, on shipper, eng and adopt-dont-shop. A sweep that edits files cannot change those settings. It can only say so.

The tables also admit what was not checked. COMMON-27 and COMMON-33 were not checked in any repo, because the sweep’s API access was blocked.

There is an open disagreement too. Two rules say shipper workflows are called by @v1, but agent-idea and this website pin an exact commit, with a CI check that the pins match. The tables say the rule needs a decision. We have not made it yet.

What we learned

  • Write the check with the rule. If you cannot say how to test it, it is advice, not a standard.
  • Separate what an agent can fix from what a person must. Files go in a PR. Settings and secrets go on a list with a name beside them.
  • Say what was not checked. A gap table that only lists failures reads as a clean bill of health for everything else.
  • Let the rule lose to the repo when the repo is right. The pinning disagreement is a rule to change, not a repo to fix.
