Built, with no users: what we did instead of launching.

AdoptDontShop is built and has no users. Here is what we did instead of launching: weeks of fixes to security and reliability, all in a public changelog.

  • By Alex Jenkinson, with support from Claude
  • 28 Nov 2026
  • 3 min read
  • Covers 21 Aug to 21 Nov 2026
  • ideaSquared/adopt-dont-shop

Where we are

AdoptDontShop is built, and it has no live users and no revenue. The venture page says so. The closed beta, with 3 to 5 rescues, is planned for early 2027.

The weeks before a beta can look quiet. They were not. The changelog on the venture page lists 78 updates since September, in 28 dated entries. The build log has 49 AdoptDontShop entries since 14 August. Much of that work was security and reliability. This post covers what we fixed and why we did it before any rescue logged in.

Why it matters for a rescue

A rescue holds applicants’ names, addresses and home details. If a volunteer sees another rescue’s applicants, or a stolen backup lets a stranger become staff, that is a real harm to real people.

Permissions and secrets

Some fixes were about who can see what.

  • 24 August. Staff invitation links carry a secret token. We had stored those tokens as plain text. A leaked database backup would have handed over ready-to-use links. Tokens are now stored in a one-way hashed form. The original email link still works.
  • 28 August and 3 September. Rescue staff could read, and then write to, an adopter’s unsubmitted application. Only the adopter can now.
  • 16 September. A staff member at one rescue could, in theory, view another rescue’s statistics by changing a request identifier. Each rescue now sees only its own data.
  • 22 September. A code defect meant six permission checks were silently not being applied. They covered admin security settings, data exports, account deletion and platform-wide pet management. The journal says: “No evidence of exploitation; fixed as part of routine security review.” We have nothing to add to that, and we will not claim more than the page says.

The common thread is a check that exists in the code but does nothing. A test that only covers the happy path will not find it.

Uploads, and what happens when a safety check fails

On 21 August every uploaded file, whether a pet photo or an application document, started going through a malware scan before reaching storage.

On 16 September we fixed a quieter problem. If the scanner could not be reached in a non-production environment, files could pass through unscanned. Uploads are now blocked whenever the scanner is unavailable, in every environment. The journal adds that no file uploaded to the live platform was ever passed through unscanned.

Two later fixes tightened this. On 14 October, files that claim to be PDFs or Word documents but contain something else are rejected. On 21 November, uploaded photos are fully re-processed, which removes hidden data such as location information. Images that cannot be processed are rejected.

A check that passed while production could not start

On 31 October every release began to pass a full smoke test before it can reach users. It boots all 14 platform services, the web gateway and the TLS edge in a production configuration, and checks live routes end to end. It replaced a partial check. The changelog says that check “was passing while the production environment could not actually start.” A green tick that means nothing is worse than no tick.

The day before, testing on a real server had already found several configuration problems that would have stopped the platform starting.

The holding page that found more

On 8 November a holding page went live at adoptdontshop.app. The same day, the changelog records three more fixes. Photo uploads were failing silently in production because of a configuration issue. Staff invitation emails were not being sent, so accepted invitations could not be acted on. And a browser security policy was blocking the brand fonts, feature settings and error reporting. All three are fixed.

Each concerned the real production setup.

What we learned

  • A missing check looks like a working one. Six permission checks sat unapplied until a review found them. Test the refusal, not only the success.
  • Decide what a safety check does when it fails. A scanner that is down should block uploads, not wave them through.
  • Test the thing users will get. A smoke test of a production configuration caught what a partial check missed.
  • Work with no users still counts. It is not a launch, and it does not show anyone wants the product. The beta numbers answer that.
