GitHub's 403 means two things.

A 403 from GitHub can mean “you may not” or “not now”. Our access check has to treat those differently, in opposite directions.

  • By Alex Jenkinson, with support from Claude
  • 28 Nov 2026
  • 3 min read
  • Covers 15 to 21 Nov 2026
  • ideaSquared/agent-idea

The gate

Agent Idea shows a product’s logs only to people who should see them. On 15 November (7e6dd9d, merged in 5ce56eb) we changed what “should” means. Before, you needed write access to the product’s repo. Now you need an active membership of the product’s GitHub team in our organisation.

The Worker does not keep a list of people. It asks GitHub, using the caller’s own token. First GET /user to learn the login, then the team membership for that login. Only a membership with state active is allowed. A pending invitation is not.

Two details from that commit. The cache of answers is keyed by team under a new prefix, team-access:, so old entries keyed by repo can never grant access. And the cache key uses a hash of the token, never the token.

When 403 means no

The first version handled 401 (bad token) and 404 (not a member). On 21 November (6708f06) we found a third case. A token that has not been authorised for SAML single sign-on, or a fine-grained token without the organisation’s Members read permission, gets a 403 from GitHub. Our check threw on it. The caller got an uncaught 500 and we wrote no audit line.

That is a denial, not a fault. The fix returned denied, so the caller gets a proper 403 that names the team they need to be in.

When 403 means wait

The same status also means a rate limit. If we cached that as “denied”, a busy afternoon would lock people out for the cache lifetime, five minutes. Our first fix, in the same commit, checked one header:

if (response.status === 403 && response.headers.get('x-ratelimit-remaining') !== '0') {
  return { outcome: 'denied', login, ...expiry };
}

That covers a spent quota. It does not cover GitHub’s secondary rate limit, which can answer 403 with quota left. The commit message for 9b505a2 says it plainly: the secondary limit is signalled only by retry-after or by the error message. So the check became a function that looks at all three:

async function rateLimited(response: Response): Promise<boolean> {
  if (response.headers.get('x-ratelimit-remaining') === '0' || response.headers.has('retry-after')) return true;
  return /rate limit/i.test(await response.text());
}

A rate-limited answer now throws, and it is not cached. Each shape has a test, and so does the cache:

['quota spent', { status: 403, headers: { 'x-ratelimit-remaining': '0' } }],
['secondary limit with retry-after', { status: 403, headers: { 'retry-after': '60' } }],
['secondary limit named only in the message', { status: 403, body: { message: 'You have exceeded a secondary rate limit.' } }],
// ...and: it('does not cache a rate-limited 403')

Reading the message text is the weakest of the three signals, but the commit notes that a secondary limit may only say so there.

The token that is about to expire

The access check also saw something useful. GitHub sends the token’s expiry date in a header on /user. On 21 November (8d1ef66) we passed it back to the CLI, and the CLI and the MCP server now print a warning on stderr when the token expires within 30 days. Tokens with no expiry never warn. The expiry is cached with the access answer.

The first version rounded down to whole days before comparing with the 30-day window. A token with a few hours left showed as “today”, and one slightly over the limit could slip under it. The fix (d1cc589) compares the exact time left, and says “in less than a day” when it is within hours. The tests added a case for each side of the line:

expect(warnings[0]).toContain('expires on 2027-11-01 (in less than a day)');
// stays quiet at 2027-12-01T12:00:00Z, and at 2027-12-15, and with no expiry

What we learned

  • One status code is not one meaning. Read the headers and the body before you decide. “Denied” and “try later” need opposite handling.
  • Never cache a temporary failure as a permanent answer. A cached rate limit turns a short problem into a lockout.
  • A denial should still leave a record. The uncaught 500 meant no audit line. Turning it into a real 403 fixed the log as well as the status.
  • Round last. Compare exact values with a threshold, and only round for display.
